startExtractThumb parses the `(as)` input, queues every path, calls
StartThumbnail at call site +0x1ab20, and returns an empty D-Bus reply.
StartThumbnail obtains a video context and calls VideoContext::Extract at call
site +0x1b6c7. No extension/media-type branch diverts a `.wma` Start request to
the separate audio cover-art context.

libthumbnailextractor.so imports libgstreamer-1.0.so.0 and gst_parse_launch. Its
pipeline literal at file offset 0x4bf40 is:
  uridecodebin name=uridecode uri=%s ! videoconvert ! videoscale ! appsink name=sink caps="%s"

Pipeline construction calls gst_filename_to_uri at +0x39037 and
gst_parse_launch at +0x39076. The autoplug-select callback at +0x38bf5 returns
skip only when the candidate factory name begins with the three-byte literal
"mfx" at +0x4bec1; it does not reject asfdemux. The requested sink caps begin
with the literal video/x-raw at +0x4bf29.

The shipped libgstasf.so registers factory `asfdemux`. Therefore a cache-miss
Start(as) request for an ASF/WMA path has a defensible static route through
uridecodebin to the exact vulnerable plugin before a later no-video/caps failure.
This is static routing evidence, not a dynamic parser or crash result for the
thumbnail process.

Invocation boundary
-------------------
The recovered edge is request-driven, not scan-time automatic:
  - the only reviewed direct caller of BrowserProvider::requestImageExtraction
    is the public requestThumbnails handler;
  - BrowserProvider::onScanCompleted (+0xe83f0) and onMediaFileFound (+0xe8510)
    forward events but have no reviewed call to requestImageExtraction,
    ExtractorInterface::requestImages, or extractor Start.

Thus a CommonAPI client can request the route statically. The evidence does not
show that USB enumeration, LightMediaScanner indexing, MediaBrowser scanning, or
a particular UI screen automatically makes that request.

Bounded VM-attempt boundary
---------------------------
Ignored exploratory logs under work/vm/vendor-userspace-260128 show the exact
thumbnail process loading libgstreamer and completing lengthy plugin/SQLite
initialization, but the temporary session bus never exposed the expected
well-known name before the probes ended. No delivered Start call, libgstasf map,
thumbnail cache output, natural process crash, or 32-versus-33 comparison was
observed. In these logs:
  - NAME_READY=0 means the name was not observed;
  - THUMB_ALIVE_*=0 means kill -0 succeeded and the process was alive;
  - CALL_RC=0 for dbus-send without --print-reply proves only local send success;
  - THUMB_WAIT_RC=1 followed harness termination and is not a parser-crash result.

Absent /dev/media0 and missing optional plugin dependencies are VM-environment
warnings, not evidence that production activation succeeds or fails. The
established V-012 PlayerEngine 32/33 controls remain separate.

Claim boundary
--------------
Established:
  exact requestThumbnails -> Start(as) contract;
  Start(as) -> VideoContext -> uridecodebin route;
  exact shipped asfdemux is eligible under the custom autoplug callback;
  route is explicitly client/request driven in reviewed code.

Not established:
  automatic scan-time thumbnail extraction;
  delivery of a thumbnail Start request in the VM;
  thumbnail-process selection of libgstasf for the 33-stream fixture;
  thumbnail-process corruption or death;
  production/head-unit reachability, controlled execution, or root transition.
