Generic file writer
Function FDE [0x140a50,0x140cae) attempts to open the supplied path with mode
10, write the supplied UTF-8 text, flush, obtain the file descriptor, and call
fsync. Its path and content are supplied by callers. It rejects open failure and
a negative write result, but does not reject zero/short writes or test flush or
fsync results; callers below do not test its return. The sites therefore prove
ordered calls, not successful, full, durable, or atomic state transitions.

Progress callback
Function FDE [0x11f1b0,0x120a9e) accepts progress in its second argument. For
accepted third-argument states, global 0x6d20ac selects the status path:
- firmware mode progress 0 attempts processing on
  /update/firmware_update_complete at 0x11ff11..0x11ff36;
- firmware mode progress 100 attempts complete on that path at
  0x120722..0x120747;
- system mode progress 0 attempts processing on /update/system_update_complete
  at 0x120571..0x120593;
- system mode progress 100 attempts complete on that path at
  0x1206b2..0x1206d7.

The progress-zero branches then test global 0x6d4f94. When it is not 1, they
attempt run on /update/force_launch at 0x11ff4c..0x11ff71 (firmware) or
0x1205a9..0x1205cb (system). These direct run calls follow the processing call,
not a complete call. The progress-100 branches instead attempt none on the
force path at 0x120754..0x120779 (firmware) and 0x1206e4..0x120709 (system).
These are branch-local orderings: later callback flow can still enter the
scheduled route and attempt run again.

Scheduled branch
The same callback separately reads and trims both status files. It requires the
system string to compare equal to complete at 0x11fb27..0x11fb62, the firmware
string to compare equal to complete at 0x120228..0x12029c, and predicate FDE
[0xe8ad0,0xe8b90) to return true at 0x1202a2..0x1202ac. It then attempts
complete on both scheduled-completion paths at 0x1202cf..0x12036c and, when
global 0x6d4f94 is not 1, attempts run on /update/force_launch at
0x120371..0x1203a7. These calls are ordered but not conditioned on verified
success of the preceding status writes.

Boundary
The direct progress-zero call sites prove that force_launch=run does not, by
itself, establish that either completion string already equals complete. The
marker has multiple origins: the later scheduled call site has stronger local
completion and schedule-state preconditions. Those strings and predicate are
operational state, and the traced call sites consume no named signature, digest,
certificate, or payload-authentication result. This write-site evidence does
not itself establish authentication, but neither does it prove that an
unauthenticated package can cause a valid upstream progress event. It also does
not establish successful status writes, update acceptance or payload writes,
slot/boot/health acceptance, root, policy escape, or persistence.
