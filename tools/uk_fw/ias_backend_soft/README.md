# ias-backend-soft build scaffold

Target: a Weston 1.10 backend plugin for the vendor Gen5W userspace that provides one 1920x720 output
named `HDMI1` plus the `ias_crtc` and `ias_mode` interfaces, with no DRM device. Scope and protocol
extraction: `evidence/vm-bringup/ias-backend-soft-scope.md`.

## Verified so far

- Cross toolchain works. The bundled zig 0.13.0 produces a valid x86-64 ELF shared object exporting
  `backend_init`:
  `work/toolchains/zig-macos-aarch64-0.13.0/zig cc -target x86_64-linux-gnu -shared -fPIC probe.c`
  `probe.c` in this directory is the toolchain proof only, not a backend.

## What the real build still needs

1. **`config.h`** — `compositor-headless.c:27` includes it; Weston normally generates it via autotools.
   A minimal stub with the `HAVE_*` defines this backend actually uses is sufficient.
2. **Generated protocol headers** — `compositor-headless.c:37` includes
   `presentation_timing-server-protocol.h`, which is generated by `wayland-scanner` from the Weston XML.
   The same applies to the IAS interfaces, whose `.xml` is not in the tree (their runtime definition was
   recovered from `ias-backend.so`; see the scope document).
3. **`wayland-scanner`** — absent from the host. Either install it or avoid the generated headers by
   writing the `wl_interface` tables directly, which is possible since the IAS tables were already
   extracted and each is small.
4. **Weston internal headers** — `compositor.h`, `pixman-renderer.h`, `shared/helpers.h` from
   `work/weston-source-1.10/full/src/`, plus `wayland-server.h` from a wayland development tree.

## Known version skew

pixman headers available on this host are **0.46.4** (Homebrew); the image ships **0.42.2** at runtime.
The `libpixman-1.so.0` ABI is stable and the calls the headless renderer makes are long-standing, but a
build against 0.46.4 headers running on 0.42.2 is a real risk to state, not to paper over. If it bites,
pin the headers to 0.42.2.

## Protocol header generation — solved, using the image's own scanner

The image ships **`/usr/bin/wayland-scanner`**, so the guest can generate Weston's protocol headers
itself and no host-side dependency is needed. `presentation_timing-server-protocol.h` in this directory
was produced this way and is committed.

Method, and the two harness facts that make it work:

1. `debugfs -w -R "write presentation_timing.xml /etc/presentation_timing.xml"` on a **CoW clone**
   (`cp -c`) of the image, never the canonical one.
2. `prepare.json` records a sha256 per artefact, so the injected image fails workspace verification until
   the hashes are recomputed. Refresh `sha256` for the changed file only; the `prepare` subcommand
   rebuilds from the official package and is not the right tool here.
3. Generate in-guest: `/usr/bin/wayland-scanner server-header /etc/presentation_timing.xml /tmp/pt.h`.
4. **Guest writes never reach the image**: the drive is `snapshot=on`, so everything written in the guest
   goes to a throwaway overlay and `debugfs dump` will not find it. My first extraction attempt failed
   exactly this way. Extract over the console instead: `busybox gzip -c … | busybox base64 | tr -d '\n'`
   between markers, then decode host-side, stripping non-base64 bytes.
5. Integrity check: the decoded size matched the in-guest size exactly (7732 bytes) and the file contains
   two `struct wl_interface` definitions, which is the expected surface for `presentation`.

The same method will generate any other protocol header the backend needs, including the Weston XMLs in
`work/weston-source-1.10/full/protocol/`.

## First successful build (verified)

`build.sh` cross-builds the **unmodified** vendored `compositor-headless.c` into a loadable plugin:

```
ELF 64-bit LSB shared object, x86-64, 35696 bytes
T backend_init
31 undefined symbols   # resolved from the weston executable at dlopen, as plugins expect
```

That settles the build question: a backend for this guest can be produced from the Weston tree on this
host, with no guest toolchain.

### Prerequisites, each established by a failure

1. **`config.h`** — committed here as a minimal stub. Weston generates it with autotools; the defines
   this backend actually needs are the handful in the file.
2. **`wayland-server.h` etc.** — from the `wayland-1.10.0` release tarball, unpacked to
   `work/vm/wayland-1.10.0-src`. Homebrew cannot supply these: the formula reports "Linux is required
   for this software" and refuses to build on macOS.
3. **`wayland-server-protocol.h`** — generated in the guest from `/usr/share/wayland/wayland.xml` by the
   image's own `wayland-scanner`, because the tarball does not ship it.
4. **`xkbcommon`** — `brew install libxkbcommon` (had a bottle; needed by `compositor.h:37`).
5. **pixman headers** — Homebrew 0.46.4 against the image's 0.42.2 runtime; skew still a stated risk.

### Getting files out of the guest

Two channels were tried and one works for large files:

- Console (gzip+b64): fine for ~8 KB, corrupts for ~23 KB. Failed on `wayland-server-protocol.h`.
- Socket capture (`/dev/ttyS1` via `--micom-serial`): **drops bytes**, 22972 in-guest vs 23064 captured,
  and gzip refused to inflate it.
- **`-chardev file,...,path=/tmp/out` on a second `isa-serial,index=2`**: lossless. Guest writes
  `busybox base64 /tmp/wp.h > /dev/ttyS2` and the host reads the file. This produced the verified
  97042-byte header, matching the in-guest size exactly.
