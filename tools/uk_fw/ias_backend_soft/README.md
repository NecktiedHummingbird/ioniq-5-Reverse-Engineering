# ias-backend-soft build scaffold

Target: a Weston 1.10 backend plugin for the vendor Gen5W userspace that provides one 1920x720 output
named `HDMI1` plus the `ias_crtc` and `ias_mode` interfaces, with no DRM device. Scope and protocol
extraction: `evidence/vm-bringup/ias-backend-soft-scope.md`.

## Verified so far

- Cross toolchain works. The bundled zig 0.13.0 produces a valid x86-64 ELF shared object exporting
  `backend_init`:
  `work/toolchains/zig-macos-aarch64-0.13.0/zig cc -target x86_64-linux-gnu -shared -fPIC probe.c`
  `probe.c` in this directory is the toolchain proof only, not a backend.

## What the real build still needs

1. **`config.h`** — `compositor-headless.c:27` includes it; Weston normally generates it via autotools.
   A minimal stub with the `HAVE_*` defines this backend actually uses is sufficient.
2. **Generated protocol headers** — `compositor-headless.c:37` includes
   `presentation_timing-server-protocol.h`, which is generated by `wayland-scanner` from the Weston XML.
   The same applies to the IAS interfaces, whose `.xml` is not in the tree (their runtime definition was
   recovered from `ias-backend.so`; see the scope document).
3. **`wayland-scanner`** — absent from the host. Either install it or avoid the generated headers by
   writing the `wl_interface` tables directly, which is possible since the IAS tables were already
   extracted and each is small.
4. **Weston internal headers** — `compositor.h`, `pixman-renderer.h`, `shared/helpers.h` from
   `work/weston-source-1.10/full/src/`, plus `wayland-server.h` from a wayland development tree.

## Known version skew

pixman headers available on this host are **0.46.4** (Homebrew); the image ships **0.42.2** at runtime.
The `libpixman-1.so.0` ABI is stable and the calls the headless renderer makes are long-standing, but a
build against 0.46.4 headers running on 0.42.2 is a real risk to state, not to paper over. If it bites,
pin the headers to 0.42.2.

## Protocol header generation — solved, using the image's own scanner

The image ships **`/usr/bin/wayland-scanner`**, so the guest can generate Weston's protocol headers
itself and no host-side dependency is needed. `presentation_timing-server-protocol.h` in this directory
was produced this way and is committed.

Method, and the two harness facts that make it work:

1. `debugfs -w -R "write presentation_timing.xml /etc/presentation_timing.xml"` on a **CoW clone**
   (`cp -c`) of the image, never the canonical one.
2. `prepare.json` records a sha256 per artefact, so the injected image fails workspace verification until
   the hashes are recomputed. Refresh `sha256` for the changed file only; the `prepare` subcommand
   rebuilds from the official package and is not the right tool here.
3. Generate in-guest: `/usr/bin/wayland-scanner server-header /etc/presentation_timing.xml /tmp/pt.h`.
4. **Guest writes never reach the image**: the drive is `snapshot=on`, so everything written in the guest
   goes to a throwaway overlay and `debugfs dump` will not find it. My first extraction attempt failed
   exactly this way. Extract over the console instead: `busybox gzip -c … | busybox base64 | tr -d '\n'`
   between markers, then decode host-side, stripping non-base64 bytes.
5. Integrity check: the decoded size matched the in-guest size exactly (7732 bytes) and the file contains
   two `struct wl_interface` definitions, which is the expected surface for `presentation`.

The same method will generate any other protocol header the backend needs, including the Weston XMLs in
`work/weston-source-1.10/full/protocol/`.

## First successful build (verified)

`build.sh` cross-builds the **unmodified** vendored `compositor-headless.c` into a loadable plugin:

```
ELF 64-bit LSB shared object, x86-64, 35696 bytes
T backend_init
31 undefined symbols   # resolved from the weston executable at dlopen, as plugins expect
```

That settles the build question: a backend for this guest can be produced from the Weston tree on this
host, with no guest toolchain.

### Prerequisites, each established by a failure

1. **`config.h`** — committed here as a minimal stub. Weston generates it with autotools; the defines
   this backend actually needs are the handful in the file.
2. **`wayland-server.h` etc.** — from the `wayland-1.10.0` release tarball, unpacked to
   `work/vm/wayland-1.10.0-src`. Homebrew cannot supply these: the formula reports "Linux is required
   for this software" and refuses to build on macOS.
3. **`wayland-server-protocol.h`** — generated in the guest from `/usr/share/wayland/wayland.xml` by the
   image's own `wayland-scanner`, because the tarball does not ship it.
4. **`xkbcommon`** — `brew install libxkbcommon` (had a bottle; needed by `compositor.h:37`).
5. **pixman headers** — Homebrew 0.46.4 against the image's 0.42.2 runtime; skew still a stated risk.

### Getting files out of the guest

Two channels were tried and one works for large files:

- Console (gzip+b64): fine for ~8 KB, corrupts for ~23 KB. Failed on `wayland-server-protocol.h`.
- Socket capture (`/dev/ttyS1` via `--micom-serial`): **drops bytes**, 22972 in-guest vs 23064 captured,
  and gzip refused to inflate it.
- **`-chardev file,...,path=/tmp/out` on a second `isa-serial,index=2`**: lossless. Guest writes
  `busybox base64 /tmp/wp.h > /dev/ttyS2` and the host reads the file. This produced the verified
  97042-byte header, matching the in-guest size exactly.

## The wrandr segfault (solved): `struct weston_output` ABI skew

Symptom: `wrandr` bound `ias_crtc` and weston died within milliseconds with `caught signal: 11`, after
`libwayland: error marshalling arguments for geometry (signature iiiiissi): null value passed for arg 5`.

The protocol code was innocent. Two controls proved it:

- A backend built from the same source **with `ias_publish()` deleted** crashed identically (same two
  log lines, same `[000000000040a860]` fault PC).
- With the instrumented build the handlers are never even reached before the crash; `bind_crtc` runs
  only after the fix.

Fault PC `0x40a860` resolves through the DWARF in `/usr/bin/weston` (not stripped) to `bind_output` →
inlined `wl_output_send_mode`, i.e. the mode loop at `output->mode_list`. The `geometry` marshal failure
one line earlier is the same defect: `output->make` read as NULL.

Cause: `work/weston-source-1.10/full/src/compositor.h` was an upstream-shaped reconstruction, but the
shipped LG `weston 1.10.0-r21_9` has a larger `struct weston_output`. It adds `pixman_region32_t damage`
**after `region`**, shifting every later member by `0x18`:

| member | vendor binary | reconstructed header (before fix) |
|---|---|---|
| `previous_damage` | 0x128 | 0x110 |
| `make` / `model` | 0x250 / 0x258 | 0x238 / 0x240 |
| `mode_list` | 0x298 | 0x280 |

So `output->base.make = "gen5w"` wrote 0x18 too low, `wl_list_init(&output->base.mode_list)` initialised
the wrong bytes, and weston's real `mode_list.next` stayed `NULL` (zalloc'd): `rbx = next - 0x10`,
`movl 0x4(%rbx)` → NULL deref.

Also absent from the reconstruction and restored the same way: `weston_output`'s trailing
`is_input_per_output`/`repeat_redraw`/`plugin` (0x308/0x310/0x318, `sizeof` 0x300 → 0x320),
`weston_seat.output_mask` (0x108, `sizeof` 0x108 → 0x110 — this one overran `struct headless_backend`),
and `weston_compositor`'s trailing `normalized_rotation`/`damage_outputs_on_init`.

Verification method, repeatable: `llvm-dwarfdump --name=<struct> --show-children /usr/bin/weston` versus
`zig cc -target x86_64-linux-gnu -Xclang -fdump-record-layouts` over `compositor.h`. All member offsets of
`weston_output`, `weston_seat`, `weston_compositor`, `weston_plane`, `weston_backend`, `weston_mode` and
`weston_timeline_object` match the binary exactly after the fix.

Second, smaller fix: `bind_crtc` now posts the `mode` event on bind, so a client sees the CRTC's mode
instead of an empty list (`wrandr` showed `CRTC = 1` with no rows before).

Result (clean two-file build in `work/vm/softbackend`): `wrandr` prints `0: 1920 x 720 @ 60000`,
`wrandr --crtc=0` exits 0, weston stays alive across both, and `weston-info` reports
`make: 'gen5w', model: 'HDMI1'`, 1920x720 @ 60 Hz.

`debug/` holds the throwaway crash-hunt scaffolding (`ias_dbg.c`, instrumented protocol copy, injector and
runner). Nothing in `debug/` is part of the shipped plugin.

The fix is tracked as `vendor-abi.patch` because `work/` is gitignored; `build.sh` applies it
idempotently (`patch -p1` from `work/weston-source-1.10/full`) before compiling, and the two-file
build it produces reproduces the injected `ias-backend-soft.so` byte for byte.

## Repository hygiene for these scripts

This repository is public and its harness rejects machine-specific paths. Every script here therefore
resolves its own location and works from any checkout:

- `debug/run_ias.py` derives the repository root from `__file__`.
- `debug/inject.sh` uses `debugfs` from `PATH`; set `DEBUGFS=/path/to/debugfs` if it lives elsewhere.
- `build.sh` uses `brew --prefix` for host headers; override `BREW_PREFIX`, `PIXMAN_INC` or `XKB_INC`
  for a different prefix.

Do not reintroduce absolute host paths when adding debug scripts. Build products (`*.so`) are gitignored
and must stay untracked: they embed the build path in their string tables.

## `ias-shot` — guest-side frame capture over `weston_screenshooter`

`ias-shot.c` is a small wayland client for the guest: it binds `wl_compositor`, `wl_shm`, the first
`wl_output` and `weston_screenshooter`, creates one 1920x720 `WL_SHM_FORMAT_ARGB8888` buffer, sends
`shoot`, waits for `done`, and writes the result as binary PPM (`P6`, RGB) to `/tmp/shot.ppm`. PPM
because neither side then needs an image library; `tools/uk_fw/ppm_to_png.py` converts it host-side.

Build with `build-shot.sh` (same conventions as `build.sh`: bundled zig, `-target
x86_64-linux-gnu.2.25`, no host wayland development tree). Two details make it link:

- `wayland-client-protocol.h`, `weston-screenshooter-client-protocol.h` and
  `weston-screenshooter-protocol.c` were generated **in the guest** by the image's own
  `/usr/bin/wayland-scanner` from `/usr/share/wayland/wayland.xml` and weston's
  `protocol/weston-screenshooter.xml`, then extracted losslessly (see
  `evidence/vm-bringup/first-hmi-frame.md`). The `code` output is needed as well as the client
  header: the `weston_screenshooter_interface` table is not in libwayland-client.
- `libwayland-client` is linked from the guest's own `/usr/lib/libwayland-client.so.0.3.0`, dumped
  out of `work/vm/softbackend/rootfs.img`, so symbol versions match the image (glibc 2.25).

Run it under weston with `--use-pixman`: the backend's default renderer is weston's noop renderer,
whose `read_pixels` does nothing, so the buffer would come back zeroed regardless of the scene.

## MICOM payload oracle — how to test a boot-info reply

`ApplicationManager` accepts or rejects the 35-byte `AskSysBootinfo` `ay` and says so in its own log. That
makes it a usable pass/fail oracle for payload work, and it took six broken instruments to get here, so the
procedure is written down.

**Precondition that cost the most time:** the helper binary must exist **in the workspace you are testing**.
`micom-service` was injected into one clone and not another, so every run invoked a missing path, failed
silently, and produced an empty log. Check first:

```sh
debugfs -R "stat /usr/bin/micom-service" work/vm/<workspace>/rootfs.img
```

**Procedure (research init is easiest — no systemd spinner to eat console output):**

1. `mkdir -p /run/dbus /run/user/root /tmp/ias /app/data`; write `root` and `messagebus` entries to `/tmp/passwd`
   (`/etc/passwd` is a symlink to it), then start `/usr/bin/dbus-daemon --system`.
2. Start `/usr/bin/micom-service` (owns `com.lge.car.micom`, serves `/Ihu`). Confirm it stays up with `pidof`.
3. Start the compositor (`ias-backend-soft.so` + `ias-shell.so`) — `ApplicationManager` will not reach
   `initBootInfo` without one.
4. Start `/app/bin/ApplicationManager`, wait ~10 s, then read `/tmp/am.log`.

**What the log means:**

| Line | Meaning |
|---|---|
| `askSysBootInfo():iface is VALID` | interface check passed — reachability is not your problem |
| `AskSysBootinfo Retry = 0/1/2` | the call got no peer (no service owning the name) |
| `AskSysBootinfo reply is VALID` | **your payload was accepted** — the signal you want |
| `initBootInfo attach fail` | the reply was received and **rejected** |

**State when this was written:** three payloads (all zeros, byte 28 = `0x01`, byte 28 = `0xFF`) were each
rejected. The acceptance criteria live in `parseMicomBootInfo`, which is stripped, logs its rejection
silently, and has no direct branch into the validity block at `0x258808`. Reachability, interface
construction and file-backed shared memory were all excluded by measurement first — so the remaining work is
reading that parser, not re-testing the plumbing.

## Boot-info stall — complete hand-off

`ApplicationManager` never completes boot-info initialisation, which keeps the launcher in its `appId 2`
retry loop (register V-036) and blocks any runtime test of V-028. Seven hypotheses have been tested and
excluded **by measurement**; this section exists so nobody re-walks them.

### Excluded, with how each was excluded

| Hypothesis | How it was excluded |
|---|---|
| D-Bus unreachable | `connect("/var/run/dbus/system_bus_socket") = 0`; `askSysBootInfo():iface is VALID` |
| Interface construction | same `iface is VALID` line — the wrapper is built correctly |
| File-backed segment path | `openat` trace: no `qipc_sharedmemory_*` and no `/dev/shm/*` opened |
| Peer absent | a peer owning `com.lge.car.micom` answered `AskSysBootinfo`; failure unchanged |
| Payload content (simple) | all-zero, byte 28 = `0x01`, byte 28 = `0xFF` — every variant rejected |
| `/dev/shm` missing | mounted a `tmpfs` there (mode 1777); failure unchanged |
| Segment existence | `ihu-shim` created the named `MICOMSTATUSMESSAGE` region; `pszSrc` still NULL |

### The one remaining unknown

The **layout and validity rules of the MICOM status structure**. Both the `ay` reply and the shared region
carry the same boot info; what a validating parser rejects is a **zero-filled** structure, which is what every
artefact this project produces contains. Evidence that this is the shape of the problem: `pszSrc NULL` is
reported *after* `initMicomShareMem() -> Start` and *before* `askSysBootInfo`, so the region is initialised
first, and a NULL source follows the same pattern as the rejected `ay`.

### Doing the remaining work

Either read `parseMicomBootInfo` / `initBootInfo` in `ApplicationManager` (stripped; anchors: `QSharedMemory::detach`
call at `0x25a42c`, `pszSrc NULL` block at `0x25a440`, validity block `0x258808`, tag `0x317c40`), or obtain the
structure from the vendor daemon: `micommanager_userspace` is the component that would populate it, and
running it with the `micom_responder` peer may produce a **populated** region whose bytes can be dumped and
used as a template — which would answer the layout question empirically instead of by reading.

### Guard rails learned the hard way

- **Check the code path ran before reading the result.** `attach fail = 0` once looked like a fix and meant
  `initBootInfo` was never entered. Verify with `grep -c 'initBootInfo'` before believing any absence.
- **Check the binary exists in the workspace under test.** Five runs were spent invoking a missing path.
- **Console markers are unreliable under systemd** (spinner rewrites). Prefer the research init, or write
  counts rather than prose.
